### 4.2. Как доказан RED

Исправления R1–R6, R8, R10 писались раньше тестов (предыдущее окно работы), поэтому RED доказан **мутацией**: рабочие файлы скопированы в резервную копию, в них воспроизведено прежнее поведение, targeted-набор запущен и зафиксирован RED, файлы восстановлены.

Воспроизведено 8 прежних поведений: съеденная отмена; окно источника следует за якорем; пересобранный источник отматывается на якорь; chunk откатывается к всему диапазону; якорь без проверки диапазона; шкала скроллится всегда; нет цикла сверки; запрос review без предела.

Результат: **141 тест, 13 failures** — падение по каждой из 8 мутаций (каждая мутация ломала свои тесты, а не чужие). После восстановления из резервной копии — `BUILD SUCCESSFUL`, полный набор зелёный.

R9 и R11 доказаны RED мутацией отдельно:

- **R9.** `floorToHour` в `HistoryRange.kt` заменён на округление часа по локальной зоне (`atZone(ZoneId.systemDefault()).truncatedTo(HOURS)`) — `chunkedRangeCutsTheWindowAtTheUtcHourLikeThePwa` упал с `expected: <1.7933616E9> but was: <1.7933598E9>` (ожидалось 12:00 UTC, получено 11:30 UTC — граница по локальному часу вместо UTC). После восстановления — `PASSED`;
- **R11.** `nextChunkForPlayback` всегда возвращал `null`, то есть переход в следующий chunk был отключён — `thePlaybackContinuesInTheNextChunkWhenTheRecordingEnds` упал, а `thePlaybackStopsAtTheLastChunkOfTheWindow` остался зелёным (мутация ломала только свой тест). После восстановления — оба `PASSED`.

Перед мутацией тест R9 был усилен: зона по умолчанию JVM на время теста принудительно меняется на `Asia/Kolkata`. Без этого старая реализация проходила тот же тест на машине, чьи часы идут по UTC, и RED был бы недоказуемым.

- доставка WS-кадра `reviews` на Android проверена по серверному коду и синтетическим кадрам, а не против живого Frigate;
- гонку R1 (отмена) нужно надёжно воспроизвести на медленной камере/сети — на устройстве она не воспроизводилась, поэтому подтверждение только unit-тестом.

## 5. Временная обвязка проверки (отменена)

History в приложении открывается только из карусели непросмотренных alert. Когда сервер не отдаёт непросмотренных alert за последний час, экран недостижим из UI. Для прогонки playback-smoke была собрана временная обвязка: окно карусели расширено до 7 дней и подавлен `POST /api/reviews/viewed`, чтобы не менять состояние сервера.

Обвязка помечена `TEMP-VERIFY`, после проверки полностью отменена: файлы восстановлены из резервных копий, `TemporaryVerification.kt` удалён, поиск `TEMP-VERIFY` по `app/src` не даёт совпадений. Финальная сборка (301 тест, 0 failures) собрана и установлена уже с отменённой обвязкой.

Прогон после исправлений по review (15:47–15:50) шёл под второй такой же обвязкой: `POST /api/reviews/viewed` подавлен константой `TEMP_VERIFY_MARK_VIEWED = false`, чтобы состояние сервера не менялось. После прогона обвязка снята — `ReviewController.kt` восстановлен из резервной копии, поиск `TEMP_VERIFY|TEMP-VERIFY` по `app/src` не даёт совпадений, финальная сборка (325 тестов, 0 failures) собрана и установлена уже без обвязки; на устройстве открыт Live с каруселью из двух непросмотренных alert («street / Car», 11m и 50m назад) и живыми плитками, падений в логе нет.

Ограничение по мутации: реальный `viewed` POST на устройстве выполнялся один раз, для alert, который был отмечен вручную в предыдущей части этой же задачи. Остальные проверки обходились без записи на сервер.

## 7. Известный пробел: вход в экран History

History открывается только тапом по карточке карусели непросмотренных alert. Если таких alert за последний час нет, карусель скрыта, а экран архива недостижим из UI — хотя в PWA запись открывается из списка событий (`web/src/pages/Events.tsx` рендерит `RecordingView`), и список событий доступен всегда.

Это расхождение с PWA, а не дефект сборки: план (`docs/superpowers/plans/2026-10-30-pwa-history-android.md`, задача 8) сознательно определяет единственный вход как «тап по review в карусели». Расширение входа (например, тап по событию в разделе Events приложения) — отдельная задача с новым дизайном.

## 8. Соответствие PWA и оговорка о версии

Сверка велась с upstream checkout `<upstream-checkout>/frigate` (только чтение, не запускался):

- цепочка экрана записи в PWA: `Events.tsx` → `RecordingView` → `DynamicVideoPlayer` → `HlsVideoPlayer` → `VideoControls`. Экран записи PWA пользуется общей панелью `VideoControls` с включённым `playbackRate: true` (`HlsVideoPlayer.tsx:483`), поэтому список скоростей экрана записи — это `PLAYBACK_RATE_DEFAULT = [0.5, 1, 2, 4, 8, 16]` (`VideoControls.tsx:57`) — совпадает с `HISTORY_SPEEDS`;
- подпись скорости `${playbackRate}x` — совпадает с `historyRateLabel`;
- автоскрытие панели на мобильном: PWA показывает панель при старте воспроизведения и прячет её через 4000 ms (`HlsVideoPlayer.tsx:635`, `setTimeout(() => setControls(false), 4000)`), тап по кадру переключает панель (`HlsVideoPlayer.tsx:556`) — совпадает с `HISTORY_CONTROLS_TIMEOUT_MILLIS = 4_000L` и тапом по кадру приложения;
- отступ начала записи 4 s (`REVIEW_PADDING`) — совпадает;
- окно по умолчанию — последние 24 часа, отдельный выбор дня — совпадает с `HistoryRange.initial` / `daySeconds`;
- hour-chunk окно VOD и inpoint-смещение — соответствуют `getChunkedTimeDay`/`findChunkIndex` и поведению vod-эндпоинта;
- переход в следующий chunk в конце записи: PWA (`RecordingView.tsx:265`, `onClipEnded` → `setSelectedRangeIdx(idx + 1)`) продолжает воспроизведение со следующим часовым chunk — совпадает с поведением приложения после R11.

Оговорка: совпадение версии развёрнутого у пользователя PWA с этим checkout **не установлено** — сверка велась с исходниками Frigate, а не с развёрнутой сборкой. Расхождения checkout ↔ развёрнутая версия PWA не проверялись.

### Детали паритета, разобранные по исходникам

- **Границы часовых chunk (R9).** PWA (`web/src/utils/timelineUtil.tsx`, `getChunkedTimeDay`) обнуляет минуты и секунды **в UTC** (`startDay.setUTCMinutes(0, 0, 0)`), а следующую границу получает прибавлением локального часа (`startDay.setHours(startDay.getHours() + 1)`) — минутное поле при этом остаётся нулевым, поэтому границы chunk идут по часу UTC в любом поясе, а в UTC+5:30 приходятся на локальную половину часа. Приложение округляет час по UTC (`floorToHour` в `HistoryRange.kt`) — теперь это совпадение, а не расхождение. Последний chunk у PWA заканчивается на `Math.floor(timeRange.before)`, промежуточные — на `endOfHourOrCurrentTime` (`web/src/utils/dateUtil.ts`, `min(конец часа, сейчас)`); приложение обрывает последний chunk тем же `floor(range.before)`, а ограничение «не дальше текущего момента» для окна, заканчивающегося не позже сейчас, не срабатывает.
- **Переход в следующий chunk (R11).** Реализовано: `nextChunkForPlayback` выбирает следующий chunk окна, `onPlaybackEnded` в `HistoryScreen` переносит якорь на его начало и продолжает воспроизведение; последний chunk окна завершает playback. Расхождение с PWA устранено.
- **Корзины движения (R7).** Расхождения с PWA нет: `web/src/hooks/use-motion-segment-utils.ts` округляет событие движения в целых миллисекундах до ближайшей половины сегмента и берёт значение по сетке 7.5 s — приложение делает ровно то же (`motionBucket`). Сервер отдаёт движение в корзинах по `scale = round(segmentDuration / 2)` (8 s на зуме 15 s) и в PWA, и в приложении; пересчёт на сетку отображения одинаков.
- **Обновление карусели.** Тема `reviews` сервера (`frigate/review/maintainer.py`, `frigate/comms/ws.py`) публикует `{type: new|update|end, before, after}`, где `after.severity` и `after.data.objects` совпадают с ожидаемым `ReviewUpdates.parseUpdate`; частота обновления карусели повторяет PWA (1/6/5 s).
- **Набор кнопок панели.** PWA включает в панели записи volume, seek, playbackRate, snapshot и fullscreen (`HlsVideoPlayer.tsx:483`), приложение повторяет этот набор; `plusUpload` (функция Frigate+ для администратора) не воспроизводится.

### Остающиеся расхождения

- Второе представление события в PWA (`web/src/views/events/EventView.tsx`) предлагает скорости `[4, 8, 12, 16]` и стартует на 8×, а панель не скрывает по таймеру вовсе (`show={!scrubbing || controlsOpen}`). Это другой экран PWA, а не экран записи; приложение воспроизводит именно представление записи (`RecordingView`) и следует принятому макету `docs/design/live-pwa-history.html` (список `[0.5,1,2,4,8,16]`, старт 1×). Расхождение зафиксировано, а не исправлено.

- Строки шкалы History в приложении заливаются плоским цветом, а не горизонтальным градиентом, как в PWA и в макете `live-pwa-history.html`. Это решение владельца ради гладкости: градиент давал 43% «рваных» кадров на панели Timeline, плоский цвет с Offscreen-слоем — 5,6% (`dumpsys gfxinfo`, SM-S901E, 120 Гц). Статичный образец: `docs/design/history-timeline-flat.html`.
- Устройство: прогон 2026-11-02 — JVM 462 теста без падений; instrumentation 85 из 86. Тест `realServerPreviewDecodesAndAdvancesThenReleases` удалён по решению владельца: он требовал более 8 кадров за 15 с, а свежее превью сервера даёт около одного кадра за 3–4 с при 8-кратной скорости (позиция идёт, ошибок нет); условие зависело от плотности кадров превью.

## 9. Итог
